## 2. 使用规则

- 文档一次只讨论一个 `目标版本`。
- 每次维护“最近更新”时，新增记录后必须裁剪为最新 5 条（按时间倒序）。
- 每条需求必须包含 `target_version`、`requirement_id`、`acceptance_criteria`。
- 本文档不维护执行状态。
- 进入执行时，条目平移到 `roadmap-00` 并保留同一 `requirement_id`。
- 涉及“结构化抽取字段与通用信息字段合并展示”的条目，`acceptance_criteria` 必须显式包含：展示事实源、字段映射、更新策略、兼容边界。

### 4.2 需求详细说明

#### `REQ-v0.1.15-001` 新增操作记录页面

- `target_version`: `0.1.15`
- `requirement_id`: `REQ-v0.1.15-001`
- `status`: `CONFIRMED`
- `title`: 新增操作记录页面
- `execution_ref`: `docs/02-roadmap/roadmap-00-todolist.md`
- `acceptance_criteria`:
  1. 页面能力：系统新增“操作记录”页面，提供日志列表查询能力，并支持按操作时间范围、操作人、操作模块、操作类型、业务对象类型、业务对象 ID、业务对象名称、操作结果、请求来源等条件进行多条件筛选，同时支持查看单条记录详情。
  2. 留痕范围：系统需对招聘业务中的关键人员操作、数据变更、流程流转和系统使用行为进行统一留痕，至少覆盖用户与权限、岗位配置、评分表管理、候选人档案维护、阶段流转、自动评分触发等关键链路。
  3. 日志记录表：系统新增统一日志记录表，至少包含 `log_id`、`operation_module`、`operation_type`、`biz_object_type`、`biz_object_id`、`biz_object_name`、`operator_user_id`、`operator_name`、`operated_at`、`operation_result`、`client_ip`、`request_source`、`remark` 等基础字段，并支持后续扩展附加上下文。
  4. 详情与比对：日志详情页需支持展示完整基础字段、备注说明与扩展上下文；当同一业务对象存在相邻历史操作时，页面应支持关键字段高亮比对，便于审计人员快速识别前后变化。
  5. 导出能力：页面需支持对当前筛选结果进行导出，并支持导出单条日志详情，导出格式至少覆盖结构化 `JSON`，便于核查留档与线下传阅。
  6. 结果记录：关键操作成功或失败后均需写入日志，并能明确区分操作结果；当业务对象存在名称或编号时，日志中需保留可读标识，便于页面检索与审计核查。
  7. 安全与审计：操作记录页面默认只读，不提供前端人工编辑或删除入口；日志写入后需作为审计事实保留，不因常规业务编辑而被覆盖。
  8. 兼容约束：不影响现有岗位管理中的关键操作日志展示能力，已有岗位级日志可继续保留，后续可逐步收敛到统一日志记录机制。

#### `REQ-v0.1.15-002` 工作台记住上次查看简历

- `target_version`: `0.1.15`
- `requirement_id`: `REQ-v0.1.15-002`
- `status`: `CONFIRMED`
- `title`: 工作台记住上次查看简历
- `execution_ref`: `docs/02-roadmap/roadmap-00-todolist.md`
- `acceptance_criteria`:
  1. 选择记忆：用户在工作台点击任意候选人/简历记录后，系统需在前端保存当前选中的候选人标识，用于后续返回工作台时恢复。
  2. 返回恢复：用户从工作台切换到岗位管理、用户管理、操作记录等其他页面后，再次返回工作台时，若上次查看的候选人仍存在于当前可见候选人列表中，系统需自动恢复该候选人的选中态、简历预览与详情区内容。
  3. 列表定位：恢复成功后，候选人列表需回到对应记录附近，避免用户返回后仍需重新在列表中定位已查看的简历。
  4. 降级处理：若上次查看的候选人已被删除、当前筛选不可见或当前列表为空，系统需安全降级到当前可用的首条候选人或空态，不得出现报错或工作台区域残留脏数据。
  5. 兼容约束：不改变现有候选人列表筛选、排序、星标、详情加载与简历预览行为；仅补充“跨页返回时恢复上次查看记录”的体验能力。

#### `REQ-v0.1.15-003` 自动评分总分校验与评分项明细展示

- `target_version`: `0.1.15`
- `requirement_id`: `REQ-v0.1.15-003`
- `status`: `CONFIRMED`
- `title`: 自动评分总分校验与评分项明细展示
- `execution_ref`: `docs/02-roadmap/roadmap-00-todolist.md`
- `acceptance_criteria`:
  1. 总分校验：自动评分结果入库前，若模型返回了评分项明细，则服务端需按所有 `item_score` 累加得到维度分与总分，避免 `overall.total_score` 与评分项求和不一致。
  2. 输出兼容：维持现有自动评分结果结构兼容，继续输出 `total_score`、`max_score`、`match_level`、`summary`、`risk_flags` 与 `dimension_scores`，且不影响规则降级评分路径。
  3. 前端展示：工作台 AI 自动评分区块需完整展示所有维度及其下全部评分项，至少包含评分项名称、得分、判定标准、判定理由、命中证据与置信度。
  4. 复核可读性：维度标题需保留维度小计，评分项需按维度归类展示，避免仅展示维度汇总导致无法追溯单项得分来源。
  5. 兼容约束：不改变自动评分触发、手动重评、候选人列表总分筛选与历史评分记录读取能力；历史无评分项明细的记录保持可读，不因前端渲染升级报错。

#### `REQ-v0.1.15-004` 上传评分表解析补全维度下评分项

- `target_version`: `0.1.15`
- `requirement_id`: `REQ-v0.1.15-004`
- `status`: `CONFIRMED`
- `title`: 上传评分表解析补全维度下评分项
- `execution_ref`: `docs/02-roadmap/roadmap-00-todolist.md`
- `acceptance_criteria`:
  1. 分段表格识别：评分表上传解析需支持“维度标题行 + 评分项行 + 续行评分标准”的分段结构；当某行仅包含维度标题时，后续评分项与续行标准应归入该维度。
  2. 评分项继承：当评分项首行写在维度列、后续标准行维度列为空时，解析器需继承最近一次有效的维度与评分项，输出完整的 `dimension`、`point`、`criterion`、`score` 关系。
  3. 结构兼容：上传评分表预览与岗位快照构建继续沿用现有 `headers`、`rows`、`dimensions`、`score_items` 结构，避免影响已接入的前端预览和自动评分链路。
  4. 兼容边界：现有包含明确“维度/评估点/评分标准/分值”表头的平铺评分表继续按原规则解析；若无法识别为分段结构，则维持现有降级解析行为。
