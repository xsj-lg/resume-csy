## 2. 文档职责（MUST）

- `req-00-draft.md`: 讨论候选需求，不维护执行状态。
- `req-01-business-terms-definition.md`: 术语与枚举语义。
- `req-02-latest-features.md`: 已发布能力事实快照。
- `roadmap-00-todolist.md`: 当前目标版本执行清单。
- `roadmap-01-task-history.md`: 已发布版本历史事实。

## 3. 编号与状态（MUST）

需求编号：
- `REQ-v<MAJOR.MINOR.PATCH>-NNN`（例：`REQ-v0.1.0-001`）

讨论状态（`req-00`）：
- `DRAFT` / `CONFIRMED` / `DEFERRED` / `REJECTED`

执行状态（`roadmap-00`）：
- `PENDING` / `IN_PROGRESS` / `BLOCKED` / `CANCELLED` / `DONE`

发布历史状态（`roadmap-01`）：
- 固定 `DONE`

## 4. 闭环流程（MUST）

1. 在 `req-00` 记录需求。
2. 需求进入执行时，从 `req-00` 平移到 `roadmap-00`（保留同一 `requirement_id`）。
3. 开发执行仅在 `roadmap-00` 维护状态。
4. 发布时把 `DONE` 归档到 `roadmap-01`。
5. 发布后回填 `req-01`（术语）和 `req-02`（能力事实）。
6. 发布归档完成后，清空 `req-00` 与 `roadmap-00` 的已发布版本条目，并切换到下一目标版本。

补充约束（MUST）：
- 若用户明确确认“已发布完成”“已经发布”“功能已上线/已完成发布”等含义，且该确认针对当前 requirement 或当前目标版本，则视为真实发布事实输入。
- 收到上述确认后，必须在同次文档维护中同步完成 `roadmap-00` 状态收口、`roadmap-01` 归档以及 `req-01/req-02` 回填，不得只记录口头确认而遗漏状态迁移。

## 5. 交付粒度（MUST）

- 每个 `requirement_id` 独立管理。
- 每个 `requirement_id` 完成后独立提交。
- 单次提交不混入多个 `requirement_id` 的功能实现。

## 6. 信息融合类需求规则（MUST）

- 适用范围：需求包含“简历结构化抽取字段”与“候选人通用信息字段”的合并展示、回填或替换。
- `req-00` 条目中必须明确以下内容并可验证：
  - 展示事实源（以哪组字段为最终展示来源）。
  - 字段映射关系（结构化字段到通用信息字段的归并清单）。
  - 更新策略（抽取更新时，展示数据如何刷新与回写）。
  - 兼容边界（历史数据无结构化结果时的展示口径与降级行为）。
- 未满足上述四项的条目不得进入 `CONFIRMED` 或平移到 `roadmap-00`。
