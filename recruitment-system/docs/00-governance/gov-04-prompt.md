## 2. 核心原则
1. Codex 可以先阅读、分析、定位问题、提出方案。
2. 只要涉及新增、修改、删除任何文档或代码文件，必须先向用户说明：
   - 准备修改的文件路径
   - 修改目的
   - 预计影响范围
3. 在用户明确同意前，Codex 不得执行任何写入操作。
4. 用户若只要求分析、起草、审阅，默认只输出建议，不直接落盘。
5. 若需求在执行过程中发生变化，任何新增修改范围也必须重新获得用户同意。
6. 修改已有文档时，必须保持原有文档的结构、编号、章节顺序、表格格式、历史记录格式与字段完整性。
7. 若新增或调整某条需求、规则或条目，同时存在关联的概览表、最近更新、摘要、索引、状态表等位置，必须一并检查并同步更新，避免只改正文、不改摘要。
8. 提交前必须进行一致性自检，重点检查编号是否连续、概览与详细说明是否一致、最近更新与实际修改是否一致，以及目标版本、状态、标题、summary 是否同步。
9. 若用户明确确认某条需求或某个版本“已发布完成”，必须将该确认继续落实到关联状态文档，不得遗漏 `roadmap-00`、`roadmap-01`、`req-01`、`req-02` 的闭环更新。

## 3. 标准交互模版
### 3.1 执行前
Codex 在开始任务时应先说明：
- 我对任务的理解
- 我将先做哪些只读检查
- 如需修改文件，会先征求你的确认

参考话术：
`我先检查相关目录和现有文档结构，整理出建议修改方案；在你确认前，我不会直接修改文件。`

### 3.2 准备修改时
Codex 必须先明确告知拟变更内容。

参考话术：
`我准备修改以下文件：`
- `docs/00-governance/gov-04-prompt.md`

`修改目的：补充交互模版治理规则，明确每次执行任务后，凡涉及文件修改，必须先获得用户同意。`
`如果你确认，我再开始写入。`

### 3.3 用户确认后
只有在用户明确回复以下含义之一时，才可执行修改：
- `同意修改`
- `可以开始`
- `按这个方案执行`
- 其他表达明确授权的语句

### 3.4 交付后
Codex 应说明：
- 实际修改了哪些文件
- 修改内容摘要
- 是否还有待你确认的后续变更

## 4. 禁止事项
- 不得在未获同意时直接创建文件。
- 不得在未获同意时直接覆盖、删除、重命名文件。
- 不得把“用户提出了需求”视为“用户同意修改”。
- 不得省略变更说明，直接进入写入阶段。

## 5. 与其他治理规则的关系
- 本规则作为交互层治理规则生效。
- 若与其他文档冲突，以“先获得用户同意再修改文件”为优先原则。
- 其他执行、需求、发布规则仍以 `docs/00-governance/` 下既有治理文档为准。
